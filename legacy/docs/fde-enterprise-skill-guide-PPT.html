02

企业 AI 的难点，不在 Demo，而在最后一公里

技术可运行只是第一步。生产、采纳和复用分别需要新的证据、角色与门禁。

DEMO能演示

模型能回答、流程能跑通、界面能展示。

GAP 1可生产

身份、权限、日志、集成、回滚与运维接管。

GAP 2有人用

真实工作流、可信输出、Champion 与反馈闭环。

GAP 3可复用

组件、模板、评估集和产品能力进入下一项目。

传统工程视角

以功能完成和技术输出衡量成功。

FDE 视角

以业务结果、风险可控和生产采纳衡量成功。

仓库作用

把高频交付动作沉淀为可重复执行和验收的能力包。

不要把 FDE 误解为驻场开发。FDE 的差异是对业务结果和产品化复用负责。仓库的价值是让最后一公里不再依赖个人英雄主义。

05

七个 Stage Gate：用证据决定是否进入下一阶段

Gate 不是文档数量检查。只有证据能支撑资源、风险和技术决策，项目才真正过门。

G0 · 立项

决策链、范围、验收、变更机制和升级路径书面化。

G1 · 发现

问题、流程、基线、边界和人工兜底清晰。

G2 · 方案

唯一主方案、淘汰项、回退和接口契约齐备。

G3 · 评估

Golden Dataset、回归、风险整改和 ROI 达标。

G4 · 生产

监控、回滚、灾备、权限与运维接管通过。

G5 · 采纳

活跃、任务成功、业务结果和运营 Owner 成立。

G6 · 复用

组件、模板、评估集、产品反馈和复盘进入资产库。

每次阶段评审都应明确：当前 Gate、缺什么证据、谁补齐、什么时候复审。不能用更漂亮的 PPT 掩盖事实和验证缺口。
06

Audit：先把人、流程和问题看清

Foundation 固化交付基线；Discovery 把模糊诉求转成可证伪业务假设。

02 DISCOVERY

  • Consultative-Problem-Solving
  • FDE-Issue-Tree-Analysis

过门证据：场景卡、As-Is、Issue Tree、基线和边界。

Discovery 的完成标志：能把需求写成“谁，在什么流程，用什么输入，达到什么指标，AI 不做什么”。
企业项目最昂贵的错误往往发生在 Discovery 不足时。强调 Business Interview、Process Mapping 和 Issue Tree 的顺序，不要一上来就做技术选型。
07

PoC Tech Stack Selector 明确要求联网检索；没有当期证据只能输出预选方案。安全门禁不要推迟到上线前，否则会导致返工甚至项目终止。

12

典型打法二：RAG、Agent、私有化三类专项路线

先验证最关键的不确定性，再增加工程复杂度。

01

企业 RAG

业务访谈与流程Issue Tree 定位问题Tech Stack SelectorRAG EvaluationDeploy → Adoption

核心门禁：小规模 Golden Dataset；解析、召回、生成、引用和采纳分层评估。

02

Agent / MCP

Problem SolvingPRD + API ReviewTech Stack SelectorTool AuditRBAC → Deploy

核心门禁：确定性流程优先；高风险动作必须确认、幂等、审计和回滚。

03

私有化 / 信创

Stakeholder + InterviewRBAC 前置Tech Stack SelectorPrivate GatewayAPI Review → Integrate

核心门禁：不仅模型落内网，还要覆盖身份、密钥、供应链、容量、灾备和接管。

RAG、Agent 和私有化是三类高频任务。共同原则是先验证业务假设和最高风险，不要为了“未来规模”在 PoC 阶段提前建设复杂平台。
13

典型打法三：主链路阻力大，或 PoC 成功但没人用

一个解决“怎么先验证”，另一个解决“为什么没形成持续使用”。

SIDECAR

体外验证，不是绕开治理

Stakeholder → Process Sidecar-AI-Transformation AIBP Collaboration 快速 PoC → Adoption 合并主链路 / 长期保留 / 终止

预先定义数据同步、权限审计、失败回退和终止条件。

ADOPTION RESCUE

使用率低，先回到真实工作流

Adoption Growth Re-interview + Re-map Process Expectation Management SQL Dashboard Executive → Product Bridge

不要只看调用量；重点看任务成功、使用成本和业务结果。

Sidecar 适合主系统改造阻力大但价值假设值得快速验证的场景。采纳修复则常常需要回退到 Discovery，而不是继续增加模型能力。
14

PoC 成功但没人用：从采纳漏斗定位真实阻塞

技术指标通过，只证明系统“能用”；企业价值要求用户“愿意用、持续用、用出结果”。

目标用户可触达
首次尝试
任务成功
持续使用
业务结果
  1. 用户是否在目标流程中真的需要该能力？
  2. 使用成本是否高于原流程或替代方式？
  3. 输出是否可信、可解释并能继续行动？
  4. 是否有 Champion、反馈入口和运营 Owner？
  5. 指标是否测任务成功与业务结果，而非只测调用量？
按漏斗逐层定位，不要把所有问题都归因于准确率。很多采纳问题来自入口、流程、信任、组织激励或缺少反馈闭环。
15

角色与责任：同一个 Gate，需要不同角色共同签字

FDE 是总控与技术业务翻译者，不是代替所有职能。

FDE / 交付负责人

阶段总控、关键取舍、结果与复用。

AIBP / 业务 Owner

业务真实性、优先级、用户和验收。

AI 工程师

可测原型、失败归因和工程质量。

架构 / IT

集成、身份、网络、运维和接管。

安全 / 合规

数据、权限、审计和整改门禁。

产品经理

规格、需求抽象和路线反馈。

客户成功 / 运营

采纳、培训、反馈和价值持续化。

高管 Sponsor

资源、优先级、阶段决策与冲突升级。

推荐机制：G0–G2 业务与技术双确认；G3–G4 IT / 安全加入门禁；G5–G6 运营与产品接棒。
避免 FDE 承担无限责任。每个 Gate 要明确谁提供输入、谁做决定、谁验收、谁接管。AIBP 双负责人机制尤其适合企业 AI 项目。
